# On-Device Basic C Compiler

  ## Summary

  Build a userspace /bin/cc command that runs on the OS, reads one basic C source file created in on-device vim, emits a native AArch64 ELF executable, marks
  it executable, and lets the existing shell run it directly.

  The first version will be a small C-subset compiler with filesystem headers in /include and compiler-owned static runtime/lib stubs. It will not implement
  dynamic linking or real /lib object loading yet.

  ## Key Changes

  - Add /bin/cc as a normal user command, host-built and embedded into the OS image like existing user programs.
  - Support CLI:
      - cc input.c -o output
      - cc input.c writes a.out
      - one source file per compile

  - Seed headers into /include during filesystem creation:
      - stdio.h, string.h, malloc.h, errno.h
      - syscall.h, fs_syscall.h, tty_syscall.h, signals.h
      - minimal stdint.h, stddef.h

  - #include <x.h> searches /include; #include "x.h" searches current directory first, then /include.
  - Generated programs are static/self-contained ELF64 AArch64 ET_EXEC files using the existing loader expectations:
      - fixed base near 0x10000
      - page-aligned PT_LOAD segments for text, rodata, data/bss
      - startup code initializes heap, calls main(argc, argv), then calls exit.

  ## Compiler Behavior

  - Implement compiler modules for lexer, tiny preprocessor, parser, semantic/type checks, AArch64 codegen, ELF writer, and bundled runtime.
  - Emit direct AArch64 machine code; do not require an assembler or linker on-device.
  - Bundle runtime implementations into generated ELFs so user code can call familiar functions like printf, puts, malloc, free, strlen, strcmp, open, read,
    write, close, lseek, chmod, and syscall wrappers.

  - Keep runtime source-compatible with the current user/lib API where practical, but do not require the compiler to compile the existing user/lib/*.c files
    in v1.

  - Implement enough C for useful OS programs:
      - types: void, char, int, long, fixed-width integer aliases, pointers, arrays, simple structs
      - declarations, globals, locals, function prototypes, function definitions
      - if, else, while, for, return, break, continue
      - calls, assignment, arithmetic, comparisons, logical ops, address/deref, indexing, casts, sizeof
      - string, char, decimal, and hex literals
      - vararg calls such as printf(...), but no user-defined vararg functions

  - Exclude for v1: floats, unions, bitfields, full macro expansion, separate compilation, dynamic linking, optimization, and full C standard compliance.

  ## Build Integration

  - Add compiler sources under a dedicated user command area, with a thin /bin/cc entrypoint and internal compiler modules.
  - Update the user command build rules so cc.elf links with the same user startup/linker path as existing programs.
  - Extend filesystem seeding to create /include and install the compiler-facing headers.
  - Use existing filesystem syscalls to write output and set execute permissions after successful compilation.

  ## Test Plan

  - Build for QEMU and RPI targets.
  - In QEMU, compile and run small programs from inside the OS:
      - hello world with printf
      - argc/argv echo
      - arithmetic/control flow factorial
      - pointers, arrays, globals, and zeroed bss
      - malloc, strlen, strcmp, memcpy
      - file IO using open/read/write/lseek/close
      - simple struct usage with filesystem or signal-related headers

  - Verify output ELF files run through the existing shell and fail cleanly on syntax/type errors.
  - Confirm generated output gets executable permissions automatically.

  ## Shared /lib Future Work

  Supporting true shared or reusable /lib code later would require a real linking model: object files or relocatable ELF input, symbol tables, relocation
  handling, ABI-stable library exports, and either an on-device linker or loader changes for dynamic libraries. For v1, static compiler-owned runtime stubs
  avoid all of that and are much simpler to make reliable.
